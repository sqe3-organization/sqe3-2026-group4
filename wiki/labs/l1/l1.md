### 2.2 Shared authentication and setup

We use the same authentication method for requests. Each member configures their own token and the permissions needed for their feature.

| Variable | Use |
| --- | --- |
| `base_url` | `https://gitlab.com/api/v4` or the v4 URL of the chosen instance. |
| `project_id` | Numeric ID of the test project. |
| `access_token` | Personal token of the account sending requests. |
| `run_id` | Identifier used to distinguish each run's data. |

1. Select a test project and check that the feature is available.
2. Generate a personal token with the necessary scopes and permissions. Store it as an API client secret.
3. Send the token in the `PRIVATE-TOKEN: {{access_token}}` header.
4. Add `Content-Type: application/json` when the request has a JSON body.
5. Check access with a read request before testing operations that modify data.

Additional roles and accounts are explained in each feature's document. We do not store tokens or cookies in the repository or screenshots.

An invalid token produces `401`; a valid token without sufficient scope may produce `403`. Access tests must account for whether the project is public or private. Reference: [REST authentication](https://docs.gitlab.com/api/rest/authentication/).

## Activity #5: Classification, priorities and team review

### 5.1 Classification and priorities

We classify cases as positive functional, negative functional, authentication/authorization, boundary and E2E. Each case states its type and priority.

| Priority | When to use it |
| --- | --- |
| P0 — Critical | Failure prevents completion of the feature's main flow. |
| P1 — High | Affects core operations, required fields or access control. |
| P2 — Medium | Affects query variants, optional fields or handling of nonexistent resources. |

<a id="convenciones"></a>

### 5.2 API testing conventions

1. **Identifier:** `TC_<FEATURE>_<METHOD_OR_FLOW>_<NNN>`; for example, `TC_WIKI_POST_001`.
2. **Title:** action + entity + condition; for example, “Reject page creation without a title”.
3. **LLTC format:** include criterion, preconditions, data, numbered steps, results per step, cleanup, type and priority. Common setup and cleanup may be in a shared section; each case states its exceptions.
4. **Data:** unique titles using `run_id`; do not use real page names as disposable data.
5. **Independence:** prepare and clean up each case's own resources; do not depend on another case or execution order.
6. **Checks:** validate status code, relevant data and persistence. For negative cases, check that no resource was improperly created, modified or deleted.
7. **Contract:** do not invent maximums, literal messages or specific status codes. Resolve uncertainties during exploration before automating checks.
8. **Environment:** configure URL, project and credentials as variables; do not store secrets in the repository.
9. **Evidence:** distinguish “Designed”, “Explored”, “Automated” and “Executed”. Record result, date, environment and screenshot or report where appropriate.
10. **Review:** each member reviews the other three members' cases, identifies the affected ID and proposes a specific correction.

The conventions and priorities are proposed by the team and should be confirmed during the final team review.
