### 2.2 Autenticación y configuración compartida

Para las solicitudes usamos la misma forma de autenticación. Cada integrante configura su propio token y los permisos que necesita para su característica.

| Variable | Uso |
| --- | --- |
| `base_url` | `https://gitlab.com/api/v4` o la URL v4 de la instancia elegida. |
| `project_id` | ID numérico del proyecto de pruebas. |
| `access_token` | Token personal de la cuenta que envía las solicitudes. |
| `run_id` | Identificador para distinguir los datos de cada ejecución. |

1. Seleccionar un proyecto de pruebas y comprobar que la característica esté disponible.
2. Generar un token personal con los alcances y permisos necesarios. Guardarlo como secreto del cliente de API.
3. Enviar el token en la cabecera `PRIVATE-TOKEN: {{access_token}}`.
4. Añadir `Content-Type: application/json` cuando la solicitud tenga un cuerpo JSON.
5. Comprobar el acceso con una consulta antes de probar las operaciones que modifican datos.

Los roles y las cuentas adicionales se explican en el documento de cada característica. No guardamos tokens ni cookies en el repositorio o en las capturas.

Un token inválido produce `401`; un token válido sin alcance suficiente puede producir `403`. Las pruebas de acceso deben tener en cuenta si el proyecto es público o privado. Referencia: [Autenticación REST](https://docs.gitlab.com/api/rest/authentication/).

## Actividad #5: Clasificación, prioridades y revisión del equipo

### 5.1 Clasificación y prioridades

Clasificamos los casos en funcionales positivos, funcionales negativos, autenticación/autorización, límite y E2E. Cada caso indica su tipo y prioridad.

| Prioridad | Cuándo usarla |
| --- | --- |
| P0 — Crítica | El fallo impide completar el flujo principal de la característica. |
| P1 — Alta | Afecta operaciones centrales, campos obligatorios o control de acceso. |
| P2 — Media | Afecta variantes de consulta, campos opcionales o manejo de recursos inexistentes. |

<a id="convenciones"></a>

### 5.2 Convenciones para las pruebas de API

1. **Identificador:** `TC_<FEATURE>_<METODO_O_FLUJO>_<NNN>`; por ejemplo, `TC_WIKI_POST_001`.
2. **Título:** acción + entidad + condición; por ejemplo, “Rechazar creación de página sin título”.
3. **Formato LLTC:** incluir criterio, precondiciones, datos, pasos numerados, resultados por paso, limpieza, tipo y prioridad. La preparación y limpieza comunes pueden quedar en una sección compartida; cada caso indica sus excepciones.
4. **Datos:** títulos exclusivos con `run_id`; no usar nombres de páginas reales como datos desechables.
5. **Independencia:** preparar y limpiar recursos propios; no depender de otro caso ni de su orden de ejecución.
6. **Comprobaciones:** validar código, datos relevantes y persistencia. En negativos, comprobar que no se creó, modificó o eliminó un recurso indebidamente.
7. **Contrato:** no inventar máximos, mensajes literales ni códigos específicos. Confirmar las dudas durante la exploración antes de automatizar las comprobaciones.
8. **Entorno:** configurar URL, proyecto y credenciales como variables; no guardar secretos en el repositorio.
9. **Evidencia:** distinguir “Diseñado”, “Explorado”, “Automatizado” y “Ejecutado”. Registrar resultado, fecha, entorno y captura o reporte cuando corresponda.
10. **Revisión:** cada integrante revisa los casos de los otros tres, señala el ID afectado y propone una corrección concreta.

Las convenciones y prioridades quedan pendientes de revisión con el equipo.
