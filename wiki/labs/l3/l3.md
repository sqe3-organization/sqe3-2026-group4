## Activity #1: Feedback and automated collection runs

### 1.1 Suggestions carried forward from Lab 2

The [previous lab](../l2/l2.md#activity-5) called for clearer response checks, repeatable setup and cleanup, and execution evidence. The migration addresses these points:

| Area | Implementation or next step |
| --- | --- |
| Response verification | Assert the expected status explicitly, check JSON headers and validate relevant body fields with Zod and Vitest. |
| Data integrity | Read resources after writes and after rejected mutations. Confirm absence after deletion. |
| Test data | Generate unique names and track resources created by a case. Wiki implements this through its test fixture. |
| Execution evidence | Keep Postman assertion totals separate from Vitest case totals. Attribute each report to its collection, command and target. |
| Response time | Record measured duration as execution context. A strict latency limit still needs an agreed requirement and measurement conditions. |

### 1.2 Automated Postman execution

Activity 1 requires automatic execution of the existing collections. Matthew uses Newman with the exported Wiki collection. The [HTML report](assets/matthew/newman_wiki_report.html) records 93 HTTP requests and 416 assertions with zero failures in 43.1 seconds. The command and scope are recorded in [Matthew's Activity 1](l3_matthew.md#activity-1). Other members keep their collection results in their own reports.

### 1.3 Difficulties and possible defects

The Wiki implementation accounts for three findings from the earlier runs:

- For the generated pages, which have no custom title in front matter, GitLab derives the display title from the last path component and renders hyphens as spaces. Assertions retain the returned slug separately from that display title.
- An empty Markdown update returned `200` with unchanged page data. The L2/code variant checks that no-op instead of claiming that the original rejection criterion passed.
- A separate `read_api` token can read a page but receives `403` for writes. This checks token scope, rather than proving a difference between project roles.

An earlier cleanup DELETE also returned `422`; a subsequent run completed successfully. Its cause was not established, so it remains an observed execution difficulty. These findings do not by themselves establish a confirmed GitLab defect. Details and limits are kept in the [Wiki report](l3_matthew.md#activity-1).

## Activity #2: API request definition

### 2.1 Language and environment

The framework uses **TypeScript**. **Bun** manages dependencies, runs scripts and executes TypeScript entry points. **Vitest runs the API tests on Node.js**. The project pins Bun `1.4.4` in [package.json](../../../package.json) and Node `26.13.1` in [.nvmrc](../../../.nvmrc) and [.node-version](../../../.node-version).

The HTTP client needs to support reusable configuration, JSON requests, negative cases, authentication and controlled timeouts. The comparison uses those requirements.

### 2.2 Request library comparison

| Criterion | Got | Axios | Ky | Native Fetch |
| --- | --- | --- | --- | --- |
| Request API | Method helpers, JSON options and reusable instances. | Method helpers, instances and request configuration. | Fetch-based method helpers and reusable defaults. | Standard `Request`/`Response` interface. |
| TypeScript | Includes types; response contracts still need runtime validation. | Includes types; response contracts still need runtime validation. | Includes types and JSON helpers. | Runtime-provided types; JSON validation belongs to the caller. |
| Shared configuration | `got.extend` combines base URL, headers, timeout and error policy. | Instances and interceptors centralize configuration. | Instances and hooks centralize configuration. | A small wrapper is needed for project defaults. |
| Negative API cases | `throwHttpErrors: false` lets tests inspect error responses. | Error handling can be customized with `validateStatus`. | HTTP error behavior can be configured. | HTTP error statuses are returned for explicit inspection. |
| Retries and timeouts | Built-in policies; the framework controls retries explicitly. | Timeout and recovery options depend on the chosen configuration. | Built-in timeout and retry options. | Abort signals support deadlines; retry policy is caller-managed. |
| Fit for this team | Matches the reference framework and the client already integrated by the team. | Familiar alternative, but would change the adopted client API. | Suitable if the team preferred a Fetch-based abstraction. | Suitable for a smaller client with more shared behavior implemented locally. |

References: [Got](https://github.com/sindresorhus/got#documentation), [Axios](https://axios-http.com/docs/intro), [Ky](https://github.com/sindresorhus/ky#readme) and [Bun Fetch](https://bun.sh/docs/runtime/networking/fetch).

### 2.3 Selected tool: Got

We selected **Got `16.2.0`** for shared connection settings, token handling, JSON responses and configurable timeouts. It also lets the tests inspect HTTP error responses directly.

The implementation stays in one [client factory](../../../src/api/client.ts). Separate clients can use editor, reader, invalid or empty tokens. `PRIVATE-TOKEN` is the GitLab-recommended header for personal access tokens; `Authorization: Bearer` is also supported. See [GitLab authentication](https://docs.gitlab.com/api/rest/authentication/#personal-project-and-group-access-tokens).

`GITLAB_RETRY_LIMIT` defaults to `0`. Tests should normally observe the first response; enabling retries is an explicit execution choice. `throwHttpErrors` is disabled so a `400`, `401`, `403` or `404` can be asserted directly. Neither setting removes the need to check the actual status.

### 2.4 Basis for the recommendation

Matthew proposed Got based on the previous TODOist testing framework, where it was already used for shared request configuration, authentication, timeouts and error handling. Since GitLab requires a similar scope, he brought that experience to the team and asked whether the approach would be useful for this project.

The comparison explains the tradeoffs behind that recommendation. The team adapted the client to GitLab. The implementation notes record local HTTP checks and live Wiki requests; their evidence is described in [Matthew’s validation section](l3_matthew.md#validation).

## Activity #3: Test runner definition

### 3.1 Test runner comparison

| Criterion | Vitest | Jest | Mocha | Bun Test |
| --- | --- | --- | --- | --- |
| TypeScript workflow | Transforms TypeScript through Vite; type checking is a separate step. | Supports TypeScript through configured transformation. | Requires a compatible TypeScript execution/transformation setup. | Executes TypeScript through Bun. |
| Assertions and mocks | Provides `expect`, mocks, hooks and fixtures. | Provides matchers, mocks and hooks. | Provides hooks and test execution; assertions/mocks can be selected separately. | Provides Jest-style assertions, mocks and hooks. |
| Parallelism | Files run in parallel by default; case concurrency is configured separately. | Worker-based execution across test files. | Supports an optional parallel mode. | Supports configurable concurrent execution. |
| Reports | CLI output, JSON/JUnit reporting, optional UI and coverage packages. | CLI/JSON reporting and reporter integrations. | Built-in reporters and additional reporter integrations. | CLI output and built-in reporting/coverage options. |
| CI use | Runs headlessly with `vitest run`. | Runs headlessly through its CLI. | Runs headlessly through its CLI. | Runs headlessly with `bun test`. |
| Team fit | Already used by the integrated Repositories and Issues modules. | Viable, but would require adapting the current setup. | Viable, with more choices to assemble. | Available, but not the runner selected for this migration. |

References: [Vitest](https://vitest.dev/guide/), [Jest](https://jestjs.io/docs/getting-started), [Mocha](https://mochajs.org/) and [Bun Test](https://bun.sh/docs/test).

### 3.2 Selected tool: Vitest

We selected **Vitest `5.1.0`** to retain the team's existing test API and configuration. [vitest.config.ts](../../../vitest.config.ts) defines source/test aliases, globals and environment setup. Assertions use Vitest; Zod checks runtime response structure. The optional UI and V8 coverage packages use the same version as the runner.

Files can run in parallel under Vitest's defaults. Wiki keeps its own cases sequential because one case compares the complete page set. `VITEST_PARALLEL` is not currently read by the configuration. An environment switch would require an explicit implementation. See [Vitest file parallelism](https://vitest.dev/config/fileparallelism.html).

### 3.3 Basis for the recommendation

Vitest was also part of the previous TODOist framework. Matthew proposed it to the team as a familiar option for organizing TypeScript cases, assertions and test lifecycle setup. The existing experience made it a practical starting point for GitLab.

The team retained Vitest while using Bun for dependency management and project scripts. The migration uses the same runner and configuration as the existing modules.

## Activity #4: Branches, commits, pull requests and CI

### 4.1 Proposed branch structure

The repository already uses `main`, `develop` and feature branches. This proposal keeps that model.

| Branch | Purpose |
| --- | --- |
| `main` | Stable team delivery. |
| `develop` | Integration of reviewed changes. |
| `feat/<short-description>` | New functionality or test modules, created from `develop`. |
| `fix/<short-description>` | Focused corrections, created from the branch receiving the fix. |
| `docs/<short-description>` | Documentation changes when a separate branch is useful. |

Sync with `develop` before opening a PR and resolve conflicts while preserving other members' changes. Merge commits are compatible with the history already used by the team; rebasing is not a mandatory policy here.

### 4.2 Commit convention

Use the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) format:

```text
<type>(<optional-scope>): <short description>
```

| Type | Use |
| --- | --- |
| `feat` | Add framework functionality. |
| `test` | Add or change test cases. |
| `fix` | Correct behavior or assertions. |
| `docs` | Update lab reports or usage instructions. |
| `chore` | Maintain dependencies and configuration. |
| `refactor` | Reorganize code while preserving its intended behavior. |

Example: `test(wiki): migrate Wiki LLTCs to Vitest`.

### 4.3 Proposed PR policy

Keep each PR focused, explain its behavior and include the validation actually performed. Request review from at least one teammate. Resolve conflicts before merging. Tokens and local environment files stay outside the diff.

For code changes, run type checking and the relevant linter/tests. For documentation, check links and consistency with the implementation. State whether a run used GitLab, a local server or simulated responses. Branch protection and required approvals are proposed rules; their remote enforcement has not been verified.

### 4.4 Proposed continuous integration strategy

There is no `.github/workflows` directory in the current checkout. The following is the proposed pipeline, not an implemented workflow:

1. Trigger checks for pull requests and pushes targeting `develop` and `main`.
2. Install the Node version from `.node-version` and Bun from `package.json`.
3. Run `bun install --frozen-lockfile`.
4. Run type checking and linting. Add a unit-test step once a local suite exists; there is currently no `tests/unit` directory.
5. Run reviewed live integration suites in a separate job with GitLab credentials and dedicated test projects. Keep Wiki cases sequential and avoid other writers during whole-list comparisons. Resolve the Issues cleanup mismatch described in Activity 6 before including that suite.
6. Retain test reports, including failure and cleanup details, as CI artifacts.

Resource IDs come from configuration or a future preparation step. A spec file should not be a prerequisite for another suite. Credentials are provided through CI secrets. `bun run test:coverage` currently targets `tests/unit`; it is not evidence of an existing coverage percentage.

## Activity #5: First requests, assertions and hooks

### 5.1 First requests

The first code-based checks should avoid creating resources: authentication, accessible listings and retrieval of known data are useful starting points. Wiki's `TC_WIKI_GET_003` needs no page fixture; the empty-list case needs a separate Wiki that is already empty. Configuration and access are still preconditions even when no test data must be created.

### 5.2 Verification tools

Use **Vitest assertions** for expected status codes, headers and business values. Use **Zod** for runtime body schemas and field types. TypeScript types describe code at compile time; they do not validate a server's JSON. The shared client returns HTTP error responses, so every test must explicitly assert its expected status.

### 5.3 Hooks and fixtures

`beforeAll`/`afterAll` surround a suite, while `beforeEach`/`afterEach` surround each case. They are useful for reusable preparation and teardown. Vitest also provides fixtures through `test.extend`, which can supply isolated data and cleanup to each test. See [Vitest test context and fixtures](https://vitest.dev/guide/test-context.html).

Wiki uses a test-scoped fixture: it creates a fresh session, passes it to the case and calls cleanup in `finally`. It registers created slugs before later assertions, deletes only its own resources and checks that they return `404`. This fixture handles the case’s setup and teardown.

## Activity #6: Migration and compatibility

### 6.1 Framework organization

| Location | Responsibility |
| --- | --- |
| [src/api/client.ts](../../../src/api/client.ts) | Shared Got client factory and request defaults. |
| [src/schemas](../../../src/schemas) | Zod response schemas. |
| [tests/integration](../../../tests/integration) | Feature specs and case assertions. |
| [tests/support/wiki.ts](../../../tests/support/wiki.ts) | Wiki test data, pagination, persistence checks and cleanup. |
| [tests/setup/load-env.ts](../../../tests/setup/load-env.ts) | Loads local `.env` values for the Node-based test process. |

Wiki keeps one spec grouped by POST, PUT, GET, DELETE and E2E. Each LLTC has its original ID and an independent fixture; it can be selected with `-t`. This follows the feature-level specs already used by the team without requiring a separate request manager.

### 6.2 Test anatomy

1. Read the required configuration and prepare only the resources needed by the case.
2. Send the request through the shared client factory.
3. Assert the exact status and applicable headers. A `204` is checked for an empty body.
4. Validate the response schema and relevant values.
5. Read again to verify persistence, unchanged state or absence.
6. Clean up owned resources even when verification fails, and report cleanup failures.

### 6.3 Compatibility and current validation

The selected stack is Got `16.2.0`, Vitest/UI/V8 coverage `5.1.0`, Zod `4.6.7`, Bun `1.4.4` and Oxlint `1.93.0`. See [package.json](../../../package.json) and [bun.lock](../../../bun.lock). Bun performs type checking with `bun check --no-script`; `@types/bun` supplies Bun API definitions. The Node-based Vitest setup explicitly loads `.env`.

The validation approach covers type checking, response schemas, HTTP behavior and test execution. Each module should record its commands, results and supporting reports in its individual document. Newman assertions and Vitest test cases are different counting units and are reported separately.

Results must distinguish requests sent to GitLab from assertions over locally constructed responses. Checks against simulated responses exercise assertions and schemas with controlled data; live requests validate integration with the API. Setup and cleanup must follow the same execution approach, and deletion must target resources actually created by the test. Suites that combine simulated setup with live cleanup need that mismatch resolved before a full run with live credentials.

The pinned Node target is `26.13.1`. Earlier local checks used Node `22.23.2`, outside the declared range (`>=26.13.1 <27`), so they do not establish compatibility with the target version. Execution on the pinned target and remote CI remains unverified.
