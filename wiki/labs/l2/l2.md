## Activity #1: Tool setup, sample requests and authorization

**Requirements:** configure an API request tool, explore it with requests to an individual sample API and implement authorization for the assigned application.

Each member uses a sample API to practise CRUD requests, then applies the shared GitLab configuration to their assigned feature.

**Shared environment:** [SQE3 — GitLab Project](assets/GitLab_Project.postman_environment.json).

The shared environment uses project ID `88312763`. Members with a separate environment follow their feature’s setup guide. Each member supplies local credentials and checks the required permissions. Requests inherit collection authorization unless a scenario explicitly tests different credentials.

<a id="token-setup"></a>

### Token and authorization setup

The collections send personal access tokens (PATs) in the `PRIVATE-TOKEN` header. Token scopes and project roles are configured for each feature:

- **Project labels (Alexis):** Uses `token_label_manager` and `token_label_reader`.
- **Project Wikis (Matthew):** Uses `token_editor` (with `api` scope) and `token_reader` (with `read_api` scope).
- **Project issues (Yeraldin):** Uses `token_reporter` (Reporter role for creation, reads and updates), `token_owner` (Project Owner for issue deletion), and `token_guest` (restricted-user scenario).

| Variable | Scope / Role | Usage |
| --- | --- | --- |
| `token_label_manager` | Permission to manage project labels | Label creation, updates and deletion. |
| `token_label_reader` | Read-only credentials | Label authorization checks. |
| `token_editor` | `api` scope / Developer+ | Access to the project; Wiki writes. |
| `token_reader` | Only `read_api` scope | Read-only access to verify scope restrictions. |
| `token_reporter` | `api` scope / Reporter | Creating, editing, closing, and reading project issues. |
| `token_owner` | `api` scope / Owner | Deleting issues permanently. |
| `token_guest` | Guest role | Credentials used by the Issues authorization scenario; check its specific operations and expected responses. |

For Wiki, the editor needs `api` and Developer or higher permissions. The reader token must have only `read_api`; both tokens may belong to the same account. Keep credential values local and export them empty.

References: [Personal access tokens](https://docs.gitlab.com/user/profile/personal_access_tokens/), [Access token scopes](https://docs.gitlab.com/security/tokens/access_token_scopes/) and [GitLab REST API Authentication](https://docs.gitlab.com/api/rest/authentication/).

## Activity #3: Preconditions, postconditions and variables

**Requirements:** evaluate implementation feasibility, define preconditions and postconditions, review variable scopes and environments, and implement multi-request flows with shared values.

| Scope | What belongs there |
| --- | --- |
| Shared GitLab environment | API base URL, project IDs, credentials and target-specific configuration. |
| Collection variables | Collection defaults and values shared across requests where needed. Reset generated IDs before starting a new case or flow. |
| Local (`pm.variables`) | Temporary test data, intermediate IDs and records of resources created by a case. Wiki resets these values before each case. |
| Globals | Avoid globals to prevent interference across test collections. |

## Activity #4: Structure and automated execution

**Requirements:** continue implementing tests with consistent ordering, structure and execution conventions, and evaluate automatic execution.

1. Keep stable case IDs (`TC_<FEATURE>_<METHOD_OR_FLOW>_<NNN>`) and descriptive English titles.
2. Group requests by feature and identify E2E flows, whether they use separate requests or a chained script.
3. Generate unique test data in pre-request scripts and document setup dependencies.
4. Check status codes, relevant headers and response fields. Add timing assertions only when a response-time requirement is defined.
5. Keep preconditions, postconditions and cleanup explicit for each case. Report setup and cleanup failures as failed tests.
6. Attempt cleanup after verification failures. Document recovery when a run stops before cleanup, and delete only resources created by the tests.
7. Run list comparisons without concurrent writers and distinguish implemented cases from executed results.

Execution instructions vary by collection:
