<a id="token-setup"></a>

### Legacy token setup for Wiki

1. In GitLab, open your avatar > **Edit profile** > **Access > Personal access tokens**.
2. Select **Generate token > Legacy token**. Enter a name and expiry date.
3. Generate the editor token with `api` and the reader token with **only** `read_api`.
4. Copy each token into its local value in the **SQE3 — GitLab Project** environment.
5. Use `token_editor` for the authorization probe and normal operations; use `token_reader` for the read-only scenario. Export both empty.

| Variable | Legacy scope | Account requirements |
| --- | --- | --- |
| `token_editor` | `api` | Access to the project; Wiki writes require Developer or higher. |
| `token_reader` | **Only `read_api`** | May belong to the same account as the editor token. |

Scopes limit the token's API access; project roles belong to the account's membership. L2 checks that read-only credentials can read a page but cannot modify or delete it. This adapts L1's role-based scenario to token-scope authorization. Adding `api` to the reader token removes the read-only scope restriction; the account’s project role still determines which writes it can perform.

References: [legacy token creation](https://docs.gitlab.com/user/profile/personal_access_tokens/#create-a-personal-access-token), [scope definitions](https://docs.gitlab.com/security/tokens/access_token_scopes/) and [scope rejection with HTTP 403](https://docs.gitlab.com/api/rest/authentication/).

## Activity #3: Preconditions, postconditions and variables

**Requirements:** evaluate implementation feasibility, define preconditions and postconditions, review variable scopes and environments, and implement multi-request flows with shared values.

| Scope | What belongs there |
| --- | --- |
| Shared GitLab environment | API base URL, project IDs, credentials and target-specific configuration. |
| Collection defaults | Defaults needed by that collection, such as its sample API URL. |
| Local (`pm.variables`) | Temporary test data, generated IDs and records of resources created by the case. Reset these values before each case. |
| Globals | Avoid globals for these tests. |

Use the shared GitLab environment for project configuration. Each feature manages its temporary data in its own scripts. Keep token values local and export them empty.

## Activity #4: Structure and automated execution

**Requirements:** continue implementing tests with consistent ordering, structure and execution conventions, and evaluate automatic execution.

1. Keep stable case IDs and descriptive English titles.
2. Group requests by feature and distinguish supporting authorization requests from test cases.
3. Create test resources in pre-request scripts. Put assertions, follow-up checks and cleanup in post-response scripts. Keep each case’s preconditions, postconditions and cleanup documented explicitly.
4. Check responses from setup and follow-up requests as well as the main request.
5. Attempt cleanup after failed verification and delete only data owned by that case.
6. Fail visibly when required configuration is missing.
7. Run cases serially when they compare complete resource lists.
8. Record the target and actual results in the individual document. Distinguish implemented tests from executed tests.

Each member includes Collection Runner or CLI instructions in Activity 4 of their document.
