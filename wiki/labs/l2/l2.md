## Activity #1: Tool setup, sample requests and authorization

**Requirements:** configure an API request tool, explore it with requests to an individual sample API and implement authorization for the assigned application.

Each member uses a sample API to practise CRUD requests, then applies the shared GitLab configuration to their assigned feature.

**Shared environment:** [SQE3 — GitLab Project](assets/GitLab_Project.postman_environment.json).

The selected project ID is `88312763`. Each member supplies their own local credentials and confirms the permissions required by their feature. Requests inherit collection authorization unless a scenario explicitly tests different credentials.

<a id="token-setup"></a>

### Token and authorization setup

Each feature uses scoped personal access tokens (PAT) or `PRIVATE-TOKEN` headers configured in local environments:

- **Project labels (Alexis):** Uses `token_label_manager` and `token_label_reader`.
- **Project Wikis (Matthew):** Uses `token_editor` (with `api` scope) and `token_reader` (with `read_api` scope).
- **Project issues (Yeraldin):** Uses `token_reporter` (Reporter role for CRUD), `token_owner` (Project Owner for issue deletion), and `token_guest` (read-only verification).

| Variable | Scope / Role | Usage |
| --- | --- | --- |
| `token_editor` | `api` scope / Developer+ | Access to the project; Wiki writes. |
| `token_reader` | `read_api` scope | Read-only access to verify scope restrictions. |
| `token_reporter` | `api` scope / Reporter | Creating, editing, closing, and reading project issues. |
| `token_owner` | `api` scope / Owner | Deleting issues permanently. |
| `token_guest` | Guest role | Checking authorization boundaries (403 Forbidden). |

References: [Personal access tokens](https://docs.gitlab.com/user/profile/personal_access_tokens/), [Access token scopes](https://docs.gitlab.com/security/tokens/access_token_scopes/) and [GitLab REST API Authentication](https://docs.gitlab.com/api/rest/authentication/).

## Activity #2: Assertions and Lab 1 implementation

**Requirements:** review Postman assertions and implement the previous lab's cases with checks for status codes, response bodies, headers and other relevant properties.

Assertions check the acceptance criteria defined in [Lab 1](../l1/l1.md):
- **Project labels (Alexis):** 17 LLTC cases covering create, read, update, rename, priority boundary, filters, and deletion.
- **Project Wikis (Matthew):** 18 LLTC cases covering page creation, retrieval, updates, attachments, Markdown rendering, and deletion.
- **Project issues (Yeraldin):** 15 LLTC cases covering issue creation, label assignment, updates, `state_event: close`, closed filter, boundary pagination (`per_page=1`), Owner deletion, and guest mutation prevention.

Follow-up requests and test assertions verify that changes were persisted or that deleted resources return `404 Not Found`.

## Activity #3: Preconditions, postconditions and variables

**Requirements:** evaluate implementation feasibility, define preconditions and postconditions, review variable scopes and environments, and implement multi-request flows with shared values.

| Scope | What belongs there |
| --- | --- |
| Shared GitLab environment | API base URL, project IDs, credentials and target-specific configuration. |
| Collection variables | Dynamic test identifiers (`run_id`, `issue_iid`, `label_name`, `page_slug`) generated during execution. |
| Local (`pm.variables`) | Temporary test data, intermediate IDs and records of resources created by a single step. |

## Activity #4: Structure and automated execution

**Requirements:** continue implementing tests with consistent ordering, structure and execution conventions, and evaluate automatic execution.

1. Keep stable case IDs (`TC_<FEATURE>_<METHOD>_<NNN>`) and descriptive English titles.
2. Group requests by feature and isolate end-to-end (E2E) lifecycle flows in dedicated folders.
3. Generate dynamic test data (`run_id = Date.now()`) in pre-request scripts to prevent naming collisions.
4. Add multi-property assertions in test scripts (HTTP status, headers like `Content-Type` and `x-per-page`, response body properties, response time).
5. Include dedicated cleanup requests to delete test artifacts even if an intermediate assertion fails.
6. Support automated execution via Postman Collection Runner and Newman CLI.

Instructions for Newman and automated execution:
- [Alexis Postman guide](postman/alexis-lab2/README.md)
